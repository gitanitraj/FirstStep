## 1. Governing execution rules

This matrix is subordinate to the approved **v2 Completion Contract** and its scope boundary.

The following rules are frozen for all IM packages:

1. **2B-P4 remains the scope boundary.** P5 could add or reshape only concepts required to complete approved v2 obligations.
2. **2B-P5 is logically complete.** Implementation work must implement or verify the approved model; it must not reopen the ER model merely because real data exposes an ordinary collision or inconvenient edge case.
3. **Code completion is not acceptance.** A package reaches `Satisfied` only when its acceptance criteria have supporting evidence.
4. **Verification precedes redevelopment.** Where an existing capability may already satisfy the requirement, inspect and test it first.
5. **Corrections must be bounded.** Verification failures authorize only the smallest change necessary to satisfy the approved v2 rule.
6. **No V3 pull-forward.** Admin dashboards, automated queues, workflow assignment, email notifications, automatic article creation, generalized relationship graphs, recommendation/personalization systems, DB migration, second-community launch, and other explicitly parked capabilities remain outside v2.
7. **Every disposition change requires evidence.**
8. **All IM-01–IM-14 packages must reach a documented terminal disposition before v2 can be declared complete.**

### Allowed execution dispositions

- **Implementation Required**
- **Implementation/Data Correction Required**
- **Verification Required**
- **Verification First — Bounded Correction If Needed**
- **Satisfied**
- **Superseded/Reinterpreted**
- **Deferred**
- **Final Closure Package**

# 6. Evidence contract for coding agents

Each coding-agent run for an IM package must return an **evidence record**, not merely “implemented.”

The minimum record is:

| Field | Required content |
|---|---|
| **Package** | Exact `IM-##` identifier |
| **Starting disposition** | One of the frozen execution dispositions |
| **Repository evidence inspected** | Files/classes/data/tests that establish current behavior |
| **Gap found** | Exact requirement not currently satisfied, or `none` |
| **Change made** | Bounded implementation/data/doc change; `none` for verification-only success |
| **Tests added/changed** | Named tests or validators and what each proves |
| **Commands / suites run** | Reproducible verification commands |
| **Result** | Pass/fail plus relevant counts |
| **Acceptance mapping** | Which package acceptance clauses were proven |
| **Journey/Epic mapping** | J1–J7 / E1–E5 supported |
| **Architecture impact** | Confirm no unauthorized P5 or V3 expansion |
| **Ending disposition** | `Satisfied`, remains open, or documented escalation |
| **Evidence reference** | Commit/diff/test output/document section used by IM-14 reconciliation |

A coding agent may **not** mark a package `Satisfied` simply because production code compiles.

# 7. Coding-agent execution rule

For each package, the agent should execute in this order:

**Inspect repository → map existing behavior to package requirements → run focused verification → identify demonstrated gap → implement smallest approved correction → add regression evidence → run broader gates → report disposition.**

The agent must not start by redesigning the domain model.

# 8. Architectural escalation rule

A real-data failure during implementation **does not reopen P5 by default**.

Escalation is justified only if implementation evidence shows that the approved model cannot represent a required v2 fact without violating an approved invariant.

The following are **not** sufficient reasons to reopen P5:

- two candidates tie;
- an existing record has bad metadata;
- an expiry date exposes an unhandled boundary;
- a flyer legitimately participates in two projections;
- a Community Event appears in both Events and Flyers;
- deterministic selection needs another regression fixture;
- a source/provider relationship was populated incorrectly.

Those are implementation, validation, or data-correction concerns.

# 9. V2 completion condition

First Step v2 is complete only when:

**IM-01 through IM-13 are terminally reconciled with evidence, IM-13 proves the seven journeys and release gates, and IM-14 establishes that the Completion Contract, historical obligations, P4/P5 baseline, documentation, implementation evidence, and explicit V3 deferrals contain no unresolved v2-required work.**

At that point—and not before—IM-14 may record the v2 closure declaration.
