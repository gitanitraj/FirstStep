# First Step v2 — Open Required Work Closure Backlog

## Purpose

This document converts every surviving **Open — v2 required** obligation from the Reconciliation Matrix into a finite closure backlog.

An item belongs here only because it is necessary to satisfy an existing Completion Contract requirement.

Completion of this backlog, followed by the final release gates and documentation reconciliation, closes v2.

---

# 1. Expiry Eligibility

**Contract:** J6 / E4  
**Type:** Domain rule + implementation  
**Priority:** First

### Decision to close

Expiry must determine whether content remains eligible for resident presentation.

The system needs three operational states:

**Active**  
The item is eligible for normal resident presentation.

**Approaching expiry**  
The item remains eligible, but requires editorial attention.

**Expired**  
The item is no longer eligible for ordinary resident presentation.

Approaching expiry is therefore **not the same thing as exclusion**.

### Required v2 work

Define one central eligibility rule that resident-facing collections use when evaluating expirable content.

The rule must apply wherever expiration is relevant rather than being independently reinvented by Category Destination, search, Updates, or another surface.

The implementation must establish:

- what field constitutes expiry;
- what happens when expiry is absent;
- when an item becomes expired;
- how “approaching expiry” is calculated;
- which resident surfaces enforce expiry;
- whether any content class is intentionally exempt because expiry has no meaning for that class.

### Important boundary

Do **not** build an automated editorial workflow.

The v2 requirement is:

> expired content is excluded where appropriate, and approaching-expiry content can be identified for human review.

### Completion evidence

This item closes when:

- expiry semantics are documented;
- known expired records no longer appear on resident surfaces where they are ineligible;
- non-expired equivalents still appear;
- approaching-expiry records remain resident-eligible;
- automated tests cover the boundary conditions;
- validators or an equivalent inspection mechanism can identify approaching-expiry records.

**Disposition after completion:** Satisfied.

# 2. Approaching-Expiry Editorial Visibility

**Contract:** J6 / E4  
**Type:** Editorial foundation  
**Dependency:** Item 1

This is deliberately separate from expiry enforcement.

### Required v2 behavior

The system must provide a reliable way for an editor/Admin to identify items that are approaching expiration.

That mechanism may be simple.

It does **not** require:

- an Admin dashboard;
- automated editorial queues;
- workflow assignment;
- email notification;
- automatic article creation.

For v2, a validator/report/diagnostic capable of producing the affected item IDs and useful expiry information is sufficient.

### Editorial consequence

The tool surfaces the condition.

The human decides what to do:

- verify the existing information;
- contact the organization;
- replace the item;
- write an “If You Go” or related piece;
- arrange an interview;
- allow the content to expire.

### Completion evidence

A repeatable command/test/report identifies approaching-expiry records correctly from actual catalog metadata.

**Disposition after completion:** Satisfied.

# 3. Expert / FAQ Category Integrity

**Contract:** J4 / J7 / E3 / E5  
**Type:** Data-integrity correction  
**Priority:** Early

### Problem

Relevant Expert and FAQ material can become invisible to Category Destinations if required category relationships are missing.

This is not a visual-design issue.

### Required v2 work

Determine the required category relationship for every Expert/FAQ record expected to participate in a Category Destination.

Then:

- correct missing data;
- validate the allowed relationship;
- ensure category projection includes eligible records;
- add a validator/test preventing silent regression.

The solution should use the existing category model rather than create a special Expert/FAQ taxonomy.

### Completion evidence

For every Expert/FAQ item expected in a category:

**record → category relationship → category API projection → resident collection**

is demonstrably intact.

Invalid or missing required relationships are caught before release.

**Disposition after completion:** Satisfied.

# 4. Flyers / Get Help Placement Rule

**Contract:** §5.2 / J1 / J4 / E2 / E3  
**Type:** Information-architecture rule  
**Priority:** Before final Category implementation

### Problem

A flyer is an artifact type, while Get Help represents resident intent.

Those are different dimensions.

A flyer can therefore legitimately belong in the Flyers informational collection while the opportunity it represents may also qualify for Get Help.

### Resolution for v2

**Placement is determined by resident meaning, not by mutual exclusivity between collections.**

A flyer remains a flyer.

If the flyer represents or points to an eligible:

- program;
- service;
- enrollment opportunity;
- fair;
- open house;
- access event;
- or comparable opportunity through which a resident can obtain help,

it may also appear in Get Help.

This does **not** create a duplicate underlying content record.

It creates two controlled projections of the same content where both resident meanings are true.

### Exclusion rule

A flyer that merely communicates information, awareness, or an announcement does not enter Get Help solely because it is a flyer.

### Completion evidence

Tests demonstrate at least:

1. flyer eligible for Flyers only;
2. flyer eligible for Flyers **and** Get Help;
3. ordinary Get Help resource that is not a flyer.

**Disposition after approval/implementation:** Satisfied.

# 5. Topic Sub-Destination Experience

**Contract:** J1 / J2 / E2  
**Type:** Resident journey  
**Priority:** Core remaining resident work

### Required journey

From a Category Destination such as Housing, a resident can select one of the available topics and enter a deeper collection of relevant help.

Example:

**Housing → Eviction Prevention → relevant programs/services/content**

The sub-destination is a **collection experience**, not another exposed taxonomy level.

### Required v2 behavior

The topic destination must:

- clearly retain category context;
- identify the selected topic;
- show relevant available content;
- foreground programs/resources/services when the resident is in the Get Help path;
- allow direct navigation to the actual underlying source/content;
- exclude content that fails resident eligibility rules;
- remain usable as inventory grows.

The design must not require every topic to have the same number or mixture of content types.

### “All Housing Help”

The broader Get Help path should expose the available non-expired help inventory rather than forcing a resident to choose one of the featured topics first.

Topics are discovery aids, not gates.

### Completion evidence

At minimum:

**Category → topic → collection → underlying item/source**

works end to end on desktop and mobile.

A resident can also enter the broader Get Help collection without selecting a featured topic.

**Disposition after completion:** Satisfied.

# 6. Featured Topic Selection

**Contract:** J2 / E2 / E5  
**Type:** Deterministic selection rule

There are two different selection problems and they should remain separate.

### A. Which topics become featured?

Initial v2 rule:

> Feature the category's subcategories with the strongest eligible content inventory.

For Housing this currently produces the kinds of topics already discussed: Eviction Prevention, Emergency Shelter, Homeownership, Rental Assistance, depending on actual eligible counts.

The selection must use **eligible content**, meaning expired/ineligible items must not inflate a topic into a featured position.

A later Admin capability may override editorially, but an Admin override system is not required for v2.

### B. Which three items appear inside a featured topic?

This is the remaining selection rule that must now be made deterministic.

The v2 selector should work by **roles**, not one undifferentiated ranking score.

For three positions:

**Position 1 — Timely / actionable**  
Prefer an eligible item whose timing matters, including an approaching-expiry opportunity when appropriate.

**Position 2 — Durable help**  
Prefer an evergreen or stable program/service/resource that gives the column continuing usefulness.

**Position 3 — Visual / additional discovery**  
Prefer an eligible flyer when the topic has one. If no flyer exists, select the strongest remaining eligible item.

This preserves the design intent already established:

- timely material earns attention;
- the column does not become entirely transient;
- a flyer adds visual interest where genuinely available.

### Tie-breaking within the same role

When multiple candidates satisfy the same role, use deterministic metadata rather than array order.

Recommended sequence:

**eligibility → role fit → recency/relevant date → stable ID**

The exact relevant date may differ by content class, but the final fallback must always be stable and reproducible.

### Important limitation

“Approaching expiry” does not automatically mean “feature this.”

It makes the item a candidate for the timely position. It must still be relevant and useful to the resident.

### Completion evidence

Given the same catalog, repeated selection produces the same:

- featured topics;
- three selected items;
- ordering.

Tests cover tie cases, missing flyers, expired candidates, and fewer-than-three eligible items.

**Disposition after implementation:** Satisfied.

# 8. Community Events Generalization Test

**Contract:** §5.4 / J7 / E5  
**Type:** Architectural acceptance test  
**Not:** A new Events project

### Question being tested

Does the architecture work when content behavior differs from Housing resources, or did we accidentally encode Housing assumptions as universal rules?

### Required v2 test

Use Community Events as the counterexample.

Verify that the relevant shared rules—community, category relationships, source/provenance, expiry/temporal eligibility where applicable, controlled projections—can operate without forcing an event to pretend to be a housing-style resource.

### Pass condition

The test may result in a small correction to a shared abstraction if an existing Contract requirement genuinely needs it.

It must **not** expand into:

- generalized event management;
- event CRUD;
- registration;
- calendars;
- recurring-event workflow;
- ticketing;
- generalized workflow management.

### Completion evidence

A documented test demonstrates that the current architecture can represent and deliver Community Events without violating the domain boundaries.

**Disposition after verification:** Satisfied.

# What Is Actually Left to Build

After reconciliation, the apparent backlog is larger than the actual implementation backlog.

The substantive remaining v2 build work is concentrated in roughly six areas:

1. expiry eligibility;
2. approaching-expiry visibility;
3. Expert/FAQ category integrity;
4. topic/Get Help collection behavior;
5. deterministic featured selection;
6. final Category Destination integration.

The Flyer/Get Help question is principally a rule that must be encoded and tested.

Community Events, provenance, multi-community readiness, accessibility, journey regression, automated suites, and documentation are principally **acceptance work**.

That distinction is important: **v2 is no longer an open-ended construction project. It is a bounded completion project.**
