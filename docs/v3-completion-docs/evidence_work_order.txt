## 1. Objective

Complete the V3A-00 implementation audit by executing and inspecting the existing application.

Determine which resident pages and behaviors:

- Already satisfy their V3A requirements.
- Exist and function but require visual restructuring.
- Are partially implemented and require functional completion.
- Are placeholders or missing.
- Cannot yet be verified because of a runtime, data, or environment limitation.

Do not assume that working components imply completed resident journeys.

Do not implement V3A design changes during this work order.

## 2. Governing authority

Use these approved references:

1. First Step v2 Completion Contract.
2. Approved 2B-P5 Logical ER + Classification Schema.
3. Authoritative IM-01–IM-14 Execution Matrix and subsequent architectural resolutions.
4. Approved V3A Homepage and Housing design decisions.
5. V3A Page Requirements & Acceptance Contract, P01–P09.
6. Approved V3A-00 through V3A-09 implementation framework.

Preserve the following architectural boundaries:

- `CivicContent`, `ContentType`, Category, Topic, Organization, ContentSource, and Community retain their approved meanings.
- V3A frontend changes must not silently alter backend classification or editorial lifecycle rules.
- The removal of the visible Get Help section must not remove the underlying All Category Help capability.
- Community Notices remains primarily nongovernment-produced information.
- Program Updates primarily represents government program and policy changes.
- First Rate News retains its approved inclusive editorial definition.
- V3B administration and stewardship capabilities remain outside V3A.

## 4. Automated baseline verification

Run the existing project verification commands as supported by the repository.

At minimum, attempt:

**Frontend**

```bash
cd frontend
npm test -- --run
npm run build
```

**Backend**

```bash
cd backend
./mvnw test
```

If the repository uses a different Maven invocation, use the documented command instead.

Also run the repository's established data validators and other existing verification scripts where available.

### Evidence requirements

For each suite record:

| Field | Required evidence |
|---|---|
| Command | Exact command executed |
| Result | PASS / FAIL / BLOCKED |
| Test count | Actual tests executed, passed, failed and skipped |
| Relevant failures | Test names and failure messages |
| Build result | Successful or failed compilation/build |
| Environment issues | Missing prerequisites or configuration |
| Evidence | Reproducible log reference |

Do not reuse historical test counts as current results.

Do not modify tests or production code to obtain a passing baseline.

## 6. Runtime acceptance method

For every page:

1. Open the route directly.
2. Confirm that it renders without an unexpected failure.
3. Exercise its principal resident action.
4. Follow at least one internal navigation pathway.
5. Use browser back/forward where applicable.
6. Inspect desktop and mobile presentation.
7. Check the relevant accessibility behavior.
8. Record whether the journey is functional.
9. Compare it with V3A requirements.
10. Assign a supported implementation classification.

Distinguish **current implementation failures** from **features intentionally deferred to V3A construction**.

Do not label a page broken simply because it does not yet match the new V3A visual design.

## 7. Implementation classification

Assign each page one classification:

| Classification | Meaning |
|---|---|
| Established | Core resident journey is functional |
| Partially Implemented | Some functionality exists but the intended journey is incomplete |
| Placeholder | Route or shell exists without meaningful resident functionality |
| Not Implemented | Required page or behavior does not exist |
| Unverified | Insufficient executable evidence to classify confidently |

Additionally assign a V3A treatment:

- Visual refinement
- Structural redesign
- Functional completion
- New implementation
- Verification only

A page may be established under v2 and still require structural redesign for V3A.

## 9. Acceptance-evidence crosswalk

For each page, report the status of its approved acceptance clauses.

Use:

- PASS — demonstrated by executable evidence.
- FAIL — tested and not satisfied.
- NOT IMPLEMENTED — required behavior is absent.
- NOT TESTED — verification was not performed.
- BLOCKED — verification could not proceed, with reason.

Reference the specific V3A acceptance IDs, such as H-01, C-02, T-04, N-02, R-05 and S-06.

Do not mark visual acceptance criteria PASS solely because equivalent JSX or CSS appears in the repository.

## 10. Risk and dependency findings

Identify:

- Missing data or DTO properties needed by an approved V3A page.
- Navigation links targeting placeholders.
- Shared components whose modification could affect unrelated pages.
- Existing API capabilities sufficient for the new presentation.
- Any backend changes that appear necessary.
- Accessibility or responsive risks.
- Differences between the working branch and earlier project documentation.

Do not solve these issues in V3A-00.

Where a backend change appears necessary, report the exact requirement and demonstrated limitation instead of implementing it automatically.

## 13. Exit criterion

V3A-00 can be marked **Satisfied** only when:

- The correct `copyofdev` baseline is confirmed.
- Existing automated test/build results are recorded.
- Every contracted resident surface has an evidence-supported implementation classification.
- Major resident journeys have been exercised where an executable environment permits.
- Missing or blocked verification is explicitly recorded.
- Functional gaps are distinguished from design changes.
- V3A-01 through V3A-09 can be planned without assuming that unfinished pages are complete.

**The final output is an evidence report—not modified application code.**
